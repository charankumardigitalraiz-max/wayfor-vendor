# Vendor Dashboard – Product & Functional Requirements

**Project:** Multi-Module SaaS Platform  
**Module:** Vendor Dashboard  
**Document Type:** Product Requirements & Frontend Implementation Specification  
**Initial Implementation:** Frontend with mock/static data  
**Future Implementation:** Backend APIs, database, GST verification and payment integration

---

## 1. Project Overview

The platform provides three independent business modules:

1. Concerts & Events – event posting, planning, management and execution.
2. Stranger Meets – planning and organizing stranger meetups.
3. Trip Pool – planning, organizing and conducting trips.

Each vendor/organization can subscribe to one or more modules and manage its own employees, module licenses, roles and permissions.

The Vendor Dashboard is the central workspace for the vendor to manage organization information, business details, GST registration, subscriptions, employees, billing and module access.

### User Types

- **Platform Admin:** Manages the complete SaaS platform, all vendors, modules, pricing, subscriptions and global configurations.
- **Vendor Admin:** Manages their own organization, subscriptions, employees, billing and module access.
- **Vendor Employee:** Uses only the modules and features assigned by their Vendor Admin.

This document covers the Vendor Dashboard only.

## 4. GST & Tax Information

### GST Registration Status

Provide two options:

- GST Registered
- GST Unregistered

If GST Registered is selected, display the GSTIN input and GST verification action.

### GST Fields

- GSTIN
- Legal Business Name
- Trade Name
- GST Registration Status
- GST Registration Date
- Constitution of Business
- Taxpayer Type
- State
- State Code
- Principal Place of Business
- Additional Business Locations, when available
- GST Registration Certificate

### GSTIN Auto-Fetch Requirement

When the Vendor Admin enters a GSTIN and clicks Verify GSTIN, the application should call a GST verification API through the backend.

The API response should automatically populate the available fields.

Example workflow:

1. Vendor enters GSTIN.
2. Frontend validates the GSTIN format.
3. Vendor clicks Verify GSTIN.
4. Backend calls the selected GST verification provider.
5. Backend receives taxpayer information.
6. Frontend displays the returned details.
7. Vendor reviews the information.
8. Vendor confirms and saves the organization details.

The application must not silently overwrite previously saved information.

### GST Verification States

- Not Verified
- Verifying
- Verified
- Invalid GSTIN
- Cancelled GSTIN
- Suspended GSTIN
- API Service Unavailable
- Verification Failed

A failed API request must not be treated as an invalid GSTIN. Provide a retry option.

### Important GST Rules

- GSTIN is 15 characters.
- Perform frontend format validation.
- Perform authoritative verification through the backend/API provider.
- Preserve the original API response and verification timestamp where appropriate.
- Allow manual correction of fields that are not returned by the provider.
- Show the source and verification date.
- Do not treat a GSTIN format check as proof of active registration.
- Do not allow a user to claim GST verification simply by entering a valid-looking number.

## 9. Module Licenses

Subscriptions belong to the organization. Licenses determine which employees can access those subscribed modules.

### License Assignment

For each employee, the Vendor Admin should be able to:

- Select an employee.
- Select a subscribed module.
- Assign a role.
- Assign permissions.
- Save the license assignment.
- Revoke access when required.

### License Information

- Organization ID
- Employee ID
- Subscription ID
- Module ID
- Role ID
- Permissions
- Assignment Date
- Assigned By
- License Status

### License Rules

- An employee cannot receive access to an unsubscribed module.
- An employee cannot be assigned more licenses than the subscription permits.
- Only active employees can receive active licenses.
- Revoked licenses should no longer provide access.
- License usage should update when assignments change.

- Browse modules
- Select plans
- Checkout simulation
- Update subscription state
- Add and edit employees
- Assign and revoke licenses
- Assign roles and permissions
- View invoices

Use local state or localStorage for prototype persistence. Provide a Reset Demo Data action.

### Backend Restrictions

Do not implement:

- Real authentication APIs
- Database connections
- Real GST verification API calls
- Real payment gateway integration
- Production email invitations
- Real document storage

Keep service functions and mock data separated so they can be replaced by backend integrations later.

## 15. Existing Project Integration Requirements

Before implementation:

1. Inspect the existing project structure.
2. Identify the current Vendor Dashboard layout.
3. Identify the existing routing and navigation conventions.
4. Identify the existing shared components and styling system.
5. Identify the existing module dashboard routes.
6. Reuse existing components wherever possible.

Do not rebuild or redesign the existing Concerts & Events, Stranger Meets or Trip Pool module dashboards.

Add Vendor Dashboard management features around the existing modules.

When a vendor or employee opens an authorized module, navigate to its existing dashboard.

Maintain consistent UI, responsive layouts, reusable forms, tables, dialogs and status indicators.

---

## 16. Access Control & Data Isolation

The production implementation must enforce the following rules:

- A Vendor Admin can manage only their own organization.
- A Vendor Admin cannot access another vendor's organization information.
- A Vendor Admin cannot change platform-wide plans or pricing.
- A Vendor Employee can access only assigned modules.
- A Vendor Employee can perform only permitted actions.
- An employee cannot access an expired or inactive subscription unless the configured policy permits it.
- All access restrictions must eventually be validated by backend APIs, not just frontend navigation or hidden menu items.

## 18. Acceptance Criteria

The Vendor Dashboard prototype is considered ready when:

- A Vendor Admin can create and update an organization profile.
- GSTIN verification can be demonstrated using mock responses.
- GST details populate the appropriate form fields.
- Registered, unregistered and invalid GSTIN scenarios can be tested.
- Billing and registered addresses can be maintained separately.
- Vendors can browse and subscribe to multiple modules using mock checkout.
- Vendors can manage their employees.
- Vendors can assign module licenses and permissions.
- Employees see only their assigned modules in the prototype.
- Subscription states and license limits are reflected correctly.
- Billing and invoice screens display consistent mock data.
- Existing module dashboards continue to work without being rebuilt.
- The complete flow works without a backend connection.
